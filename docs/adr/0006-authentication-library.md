# 0006 Authentication library: Better Auth RS

Status: proposed (2026-11-15). Becomes accepted when the M0 spike passes.

## Context

Unseen is multi-user from the start. Password hashing, sessions, cookies and
CSRF should not be written by hand. Later milestones want passkeys, 2FA and
OAuth.

State of the library, checked on 2026-11-15:

- Crate `better-auth`, repository `better-auth-rs/better-auth-rs`, docs at
  https://better-auth.rs/docs.
- Latest release: `1.0.0-alpha.5` (2026-10-21). The README says public Rust
  APIs and database schemas can change between alpha releases.
- The `seaorm2` feature exists only in `1.0.0-alpha.2` and later. The last
  stable-numbered release, `0.10.0`, only has an SQLx/Postgres adapter.
- Compatibility target: TypeScript `better-auth@1.7.6` (routes, payloads,
  cookies, errors).
- `better-auth-seaorm` requires `sea-orm ^2.0.0-rc.37`; stable 2.0.x fits.
- Axum 0.8 integration through the `axum` feature.
- CLI: crate `better-auth-cli`, binary `better-auth-rs`,
  `better-auth-rs generate --plugins <list> --output <file> [--force]`.
- The docs say builds need OpenSSL 3.0 or newer.

## Decision

- Use Better Auth RS for authentication only: sign-in, password hashing,
  sessions, cookies, CSRF, later passkeys, 2FA and OAuth. Mounted at
  `/api/auth`.
- Pin `better-auth = "=1.0.0-alpha.5"` from crates.io with features `axum`
  and `seaorm2`. Upgrade deliberately, one alpha at a time, with a migration
  when the schema changes.
- Pin the frontend `better-auth` client to `1.7.6`.
- Auth runs on our SeaORM entities through `SeaOrmStore`, sharing our
  `DatabaseConnection`. Entities are generated by the CLI into
  `crates/db/src/auth_schema.rs`, committed, and bound with
  `#[derive(AuthSchema)]`.
- `create_auth_tables` is called once, from our first migration. Every later
  auth schema change is one of our own versioned migrations.
- Migrations run before the auth instance is built.
- Authorization stays ours (ADR 0007). The admin and organization plugins are
  not used for access control, and the admin plugin is not enabled to get a
  `role` column. Our role tables reference the auth user table by id.
- M1 enables email/password and sessions only.

## Spike (M0) must confirm

1. It builds with our SeaORM, Axum and Rust versions, on Linux and Windows,
   and whether `rustls` removes the OpenSSL requirement.
2. Generated schema + `SeaOrmStore` on a SQLite file works end to end with
   sign-up and sign-in from the Svelte client.
3. Sign-up can be closed after the first user. Known: `enable_signup` on
   `EmailPasswordPlugin` is set when the instance is built; no runtime switch
   is documented.
4. Sessions can be revoked when a user is disabled. Known: the documented
   endpoints revoke only the caller's own sessions.
5. Whether the API-key plugin can serve the compat API, or we keep our own
   key table. Known: the plugin reads `x-api-key` only with
   `enable_session_for_api_keys`; Seerr sends the key as `?apikey=`.

If any check fails: stop and report. Do not switch libraries without a new
decision.

## Consequences

- Wire compatibility lets us use the official Svelte client.
- An alpha dependency in the security path: exact pin, upgrades reviewed,
  schema drift handled by our migrations.
- If checks 3 to 5 need workarounds, they are our code: an Owner-setup
  endpoint that creates the user server-side, session deletion through our
  entities, and our own `api_keys` table.
